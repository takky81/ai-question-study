# Requirements Document

## Introduction

本アプリは、選択問題に解答して学習する個人向けアプリである。現状はリポジトリに仕様駆動開発の設定と steering 文書しかなく、後続のすべての機能（科目カタログ、出題、取込・出力、統計）が共通で必要とする実行基盤（ビルド、配信、認証、データ接続、共通レイアウト）が存在しない。

app-foundation は、所有者本人だけがログインして空のホーム画面に到達できる状態を作り、後続の機能が決められた場所に画面とデータアクセスを追加するだけで実装を始められる土台を提供する。

## Boundary Context

- **In scope**: プロジェクト雛形とビルド設定、サブパス配信での画面遷移、データ基盤への接続、ログイン／ログアウト／保護された画面、公開登録の無効化、共通レイアウトとナビゲーション、テーマと正誤色を含む共通の見た目の定義、全件取得のための共通ページング、品質ゲート・CI・自動デプロイ。
- **Out of scope**: 科目・問題などの業務データの保存領域と、それを扱う業務画面（学習・管理・取込・統計の各画面の中身）。アカウントの公開登録・パスワード再設定画面。
- **Adjacent expectations**: 後続の各 spec は、本基盤が提供する認証状態、共通レイアウト、テーマトークン、ページングを再利用し、独自に再定義しない。所有者アカウントはデータ基盤の管理側で事前に作成されていることを前提とする。

## Requirements

### Requirement 1: ビルドと開発環境

**Objective:** 開発者として、決められたコマンドで開発・検査・ビルドができる雛形がほしい。それにより後続の機能をすぐに実装し始められる。

#### Acceptance Criteria

1. アプリ基盤は依存関係の導入、開発サーバーの起動、型検査、ユニットテスト、本番ビルド、E2E テスト、ローカルデータ基盤の起動・停止を、それぞれ1つのコマンドで実行できるようにする。
2. 本番ビルドを実行したとき、アプリ基盤は型エラーがなければ静的に配信可能な成果物を出力する。
3. ソースに型エラーまたは未使用の変数・import がある場合、アプリ基盤は型検査を失敗させる。
4. アプリ基盤は後続の機能が業務領域ごとのディレクトリに画面とデータアクセスを追加するだけで、ルートとナビゲーションへ組み込めるようにする。
5. アプリ基盤は接続先 URL と公開前提のキーだけを環境変数から読み込み、秘密情報を配信成果物に含めない。
6. 必要な接続設定の環境変数が欠けている場合、アプリ基盤は起動時にどの設定が欠けているかを日本語で示す。

### Requirement 2: サブパス配信と画面遷移

**Objective:** 所有者として、公開ホスティングのサブパス配下で全画面を開きたい。それにより配信先に関係なく同じ URL 構造で使える。

#### Acceptance Criteria

1. 本番配信のサブパス配下で動作している間、アプリ基盤は画面遷移・リンク・静的資産の参照をすべてそのサブパス配下で解決する。
2. 開発環境で動作している間、アプリ基盤はルートパス配下で同じ画面遷移を提供する。
3. 所有者がアプリ内の任意の画面の URL を直接開くか再読み込みしたとき、アプリ基盤はその画面を表示する。
4. 存在しない画面の URL を開いた場合、アプリ基盤は「ページが見つからない」旨とホームへ戻る導線を表示する。

### Requirement 3: 認証とセッション

**Objective:** 所有者として、自分のアカウントでだけログインしたい。それにより自分の学習データを他人に見られない。

#### Acceptance Criteria

1. 所有者が正しいメールアドレスとパスワードでログインしたとき、認証機能はセッションを開始し、ログイン前に開こうとしていた画面（なければホーム）へ遷移する。
2. 認証情報が誤っている場合、認証機能は入力内容を保持したまま日本語のエラーメッセージを表示し、セッションを開始しない。
3. 通信障害などでログイン処理が失敗した場合、認証機能は再試行できることがわかる日本語のエラーメッセージを表示する。
4. ログイン処理が進行中の間、認証機能は送信操作を無効化し、二重送信を防ぐ。
5. 所有者がログアウトしたとき、認証機能はセッションを終了し、ログイン画面へ遷移する。
6. 所有者がブラウザを再読み込みまたは再訪したとき、認証機能は有効なセッションを復元し、再ログインを求めない。
7. 認証機能はアプリ内に新規登録の導線を持たず、公開登録が無効化された状態を前提とする。
8. 未登録のメールアドレスで登録を試みた場合、認証機能はアカウントを作成しない。

### Requirement 4: 保護された画面

**Objective:** 所有者として、未ログインでは業務画面を開けないようにしたい。それによりデータが認証なしに表示されない。

#### Acceptance Criteria

1. 未ログインの間に保護された画面を開いたとき、アプリ基盤はログイン画面へ遷移し、元の画面を遷移先として保持する。
2. セッションの確認中の間、アプリ基盤は保護された画面の内容を表示せず、読み込み中の表示を出す。
3. ログイン済みの間にログイン画面を開いたとき、アプリ基盤はホームへ遷移する。
4. セッションが失効または他のタブでログアウトされたとき、アプリ基盤は保護された画面からログイン画面へ遷移する。
5. アプリ基盤は後続の機能が追加する画面を、既定で保護された画面として扱う。

### Requirement 5: 共通レイアウトとナビゲーション

**Objective:** 所有者として、学習はスマートフォンで、管理は PC で使いやすい画面構成にしたい。それにより利用場面ごとに迷わず操作できる。

#### Acceptance Criteria

1. ログイン済みの所有者がホームを開いたとき、アプリ基盤は共通レイアウト内に空のホーム画面を表示する。
2. 共通レイアウトは学習系（出題・統計）と管理系（カタログ・入出力）の導線を区別して表示し、ログアウト操作を常に提供する。
3. 画面幅がスマートフォン相当の間、共通レイアウトは学習系の導線を親指で届く位置に優先表示し、横スクロールを発生させない。
4. 画面幅が PC 相当の間、共通レイアウトは管理系の導線を含む全導線を常時表示する。
5. 共通レイアウトは現在表示中の画面に対応する導線を、色以外の手段も含めて識別できるようにする。
6. 後続の機能の画面がまだ存在しない場合、共通レイアウトはその導線を表示しない。

### Requirement 6: テーマと共通の見た目

**Objective:** 所有者として、全画面で一貫した色と操作感がほしい。それにより正誤や危険操作を取り違えない。

#### Acceptance Criteria

1. アプリ基盤は色と共通部品の見た目を共通の定義に集約し、各画面が個別の色値を持たずに参照できるようにする。
2. アプリ基盤は正解を赤、不正解を青で示す色を全画面共通で定義し、エラー・危険操作用の警告色とは別に定義する。
3. アプリ基盤はライトテーマとダークテーマを提供し、端末の設定に従って切り替える。
4. アプリ基盤は両テーマで本文・正誤色・警告色が背景に対して読み取れるコントラストを確保する。
5. アプリ基盤は選択状態と正誤状態を、それぞれ色以外の独立した表現でも示せる共通の見た目を提供する。
6. アプリ基盤は操作可能な要素に、目に見えるキーボードフォーカス表示と 44px 相当以上の操作領域を確保する。

### Requirement 7: 全件取得の共通ページング

**Objective:** 後続機能の開発者として、1回あたりの取得上限を超える件数を欠けなく取得する共通手段がほしい。それにより大量データでも行が欠落・重複しない。

#### Acceptance Criteria

1. 共通ページングで全件取得を要求したとき、ページング機能は1回あたり 1,000 件ずつ、安定した一意の順序で、取得結果が上限未満になるまで取得を繰り返す。
2. ページング機能は取得した全行を順序どおりに、欠落・重複なく返す。
3. 途中のページ取得が失敗した場合、ページング機能は部分的な結果を返さず、取得処理の文脈を含む日本語のエラーとして失敗を返す。
4. 対象が 0 件のとき、ページング機能は空の結果を返す。

### Requirement 8: 品質ゲート・CI・デプロイ

**Objective:** 開発者として、変更ごとに自動検査され main への反映で自動配信される仕組みがほしい。それにより壊れた状態を配信しない。

#### Acceptance Criteria

1. push または pull request が作成されたとき、CI は型検査、ユニットテスト、本番ビルドを実行し、いずれかが失敗したら結果を失敗とする。
2. main への反映に対する品質ゲートが成功したとき、デプロイ処理は本番ビルドの成果物を公開ホスティングへ配信する。
3. 品質ゲートが失敗した場合、デプロイ処理は配信を行わない。
4. CI とデプロイ処理は公開前提のキー以外の秘密情報を使わず、管理者権限のキーを保持しない。
5. アプリ基盤はローカルのデータ基盤に対して、ログイン・ログアウト・保護された画面の遷移・モバイル幅と PC 幅のレイアウトを検証する E2E テストを提供し、本番のデータ基盤には接続しない。
6. アプリ基盤は純粋ロジックのユニットテストを、対象モジュールの隣に置いて実行できるようにする。
